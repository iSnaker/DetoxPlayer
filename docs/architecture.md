# Архитектура DetoxPlayer

Документ описывает целевые требования. Фактическое состояние реализации
и результаты сверки с кодом: [roadmap.md](roadmap.md), основа `c8fe23d` с последующими локальными изменениями.

## Подтверждённые требования

- Windows, Docker Desktop; несколько музыкальных папок с добавлением и удалением через админку. Первая папка — `F:\Music`.
- Несколько тысяч треков, более 60 ГБ, преимущественно MP3.
- Смешанная структура папок, возможны файлы без тегов, включая `01.mp3`.
- Доступ через интернет, без аккаунтов. Выдача и отзыв ключей на компьютере сервера.
- Flutter: Android, iOS, web. При подключении вводятся адрес сервера и ключ.
- Теги и обложки, текстовый поиск, очередь, shuffle/repeat.
- На телефонах: фоновое воспроизведение, управление с экрана блокировки и гарнитуры, скачивание внутрь приложения.
- Web без офлайн-скачивания. Фоновая работа зависит от ограничений браузера и ОС.
- Плейлисты локальные для каждого устройства. В web — в локальном хранилище браузера; очистка данных браузера удалит их.
- Android Auto и CarPlay входят в целевой объём. Передача на другие устройства не требуется.
- Монорепозиторий `iSnaker/DetoxPlayer`. Первые iOS-сборки устанавливаются через Xcode.

## Предложенные решения

### Сервер

Серверный этап реализован: Python, FastAPI, Mutagen для тегов, SQLite для каталога, Docker Compose и локальная админка. Отдельный процесс клиентского API обслуживает каталог, ключи, cookie-сессии, MP3 с Range/HEAD и обложки. Инструкции: [Windows](windows-setup.md), [контракт API](client-api.md). Базовый Flutter-клиент и конфигурация внешнего HTTPS уже реализованы; оставшиеся работы перечислены в [roadmap](roadmap.md).

API и индексатор работают в Docker. Разрешённые каталоги Windows монтируются только для чтения в `/sources/<mount-name>`; первая папка — `F:/Music`. База и кэш обложек — в отдельном постоянном томе. Источники библиотеки хранятся в SQLite: постоянный ID, отображаемое название, путь внутри разрешённого монтирования и состояние. Идентичность файла определяется парой ID источника и относительного пути: одинаковые имена в разных источниках не конфликтуют. Образы и скрипты не включают музыку. Проверка недоступной папки обязательна: временная потеря диска не должна очищать весь каталог.

Первичное и повторное сканирование выполняются в фоне. На старте доступны уже проиндексированные записи. Изменения определяются по ID источника, относительному пути, размеру и времени модификации; полное хеширование всех 60 ГБ на каждом сканировании не нужно. Идентификаторы треков сохраняются в БД. Переименование и сопоставление перемещённых файлов требуют отдельного решения, чтобы не ломать локальные плейлисты.

Теги имеют приоритет. Без названия отображается имя файла, без исполнителя — «Неизвестный исполнитель». Клиент показывает относительную папку для различения нескольких `01.mp3`. Имена папок не выдаются за достоверные теги. Поиск включает название, исполнителя, альбом, имя файла и относительный путь; нужен регистронезависимый поиск на русском и английском. Абсолютные пути Windows не возвращаются клиентам.

Обложка: встроенная, затем `cover.jpg`/`folder.jpg` в папке, затем заглушка. Повреждённый трек или тег не прерывает сканирование; ошибки доступны в панели. Исходные MP3 не изменяются. Отдельно проверяется обработка старых кодировок ID3.

Аудио отдаётся по ID с HTTP Range, корректными Content-Type/Length, HEAD и отменой запросов. ID разрешается через каталог с проверкой нахождения файла внутри зарегистрированного источника после разрешения символических ссылок; произвольные пути не принимаются. Транскодирование в начальную версию не входит.

### Ключи и панель

Подтверждена локальная веб-панель вместо отдельного Windows executable. Её порт публикуется только на `127.0.0.1`; публичный reverse proxy не маршрутизирует административные endpoints. Локальная панель дополнительно защищается административным секретом и проверкой Origin/CSRF для мутаций. Проверять адрес клиента внутри контейнера как единственную защиту нельзя.

Панель: создать ключ с названием устройства, показать секрет один раз, список дат выдачи/последнего использования, отзыв ключа, запуск и состояние сканирования.

Подтверждённые функции управления медиатекой:

- Список источников: название, путь на сервере, доступность, число проиндексированных треков и состояние последнего сканирования.
- «Добавить папку»: выбрать доступную контейнеру папку в локальной панели, задать название, проверить доступность и запустить её сканирование. Выбор вложенных папок выполняется через серверный обозреватель разрешённых каталогов, а не браузерную загрузку файлов. Музыка остаётся на диске, копирования на сервер нет. Дубликаты и пересечения корней отклоняются после нормализации путей, чтобы один файл не индексировался дважды.
- «Удалить папку из библиотеки»: подтверждение с числом затронутых треков; источник и его треки исключаются из активного каталога, исходные папки и файлы на диске не удаляются. Локальные плейлисты сохраняют недоступные записи, скачанные копии остаются на устройствах. Новые запросы к исключённым трекам не обслуживаются; уже переданные байты отозвать невозможно. Настройки других источников и ключи сохраняются.
- Docker ограничивает доступ к папкам. Добавление источника внутри уже смонтированного разрешённого каталога не требует перезапуска. Для папки вне этих каталогов сначала добавляется read-only bind mount в Compose и пересоздаётся контейнер с сохранением тома БД. Панель показывает инструкцию для Windows; она не получает Docker socket и не меняет монтирования сама. По умолчанию весь диск Windows не монтируется.

- Просмотр уже проиндексированных папок и файлов: выбор источника или всей библиотеки, навигация по дереву папок, постраничный список файлов, поиск по названию, тегам и относительному пути. Источник списка — каталог SQLite; ещё не просканированные файлы не выдаются за проиндексированные. Для файла показываются относительный путь, доступные теги и состояние; для сканирования — время, прогресс, результаты и ошибки.
- «Пересканировать»: для выбранного источника или всей библиотеки найти добавленные и изменённые файлы, убрать из актуального каталога удалённые. ID неизменившихся треков сохраняются, чтобы не ломать локальные плейлисты. Удалённый трек в локальном плейлисте показывается как недоступный; скачанная копия остаётся на устройстве.
- «Сбросить индекс и пересканировать»: отдельное действие с подтверждением. MP3 перечитываются полностью; ID известных файлов в том же источнике по прежним путям сохраняются. Удаление и повторное добавление источника создаёт новые ID. Перестраивается только каталог музыки и производный кэш; исходные файлы, список источников, ключи и настройки сервера не удаляются.
- Новый индекс при полном сбросе строится отдельно и заменяет действующий после успешного завершения. При недоступности корневой папки или сбое текущий каталог сохраняется. При частичных ошибках папок/файлов сканирование помечается как неполное; отсутствующие записи в недоступных участках не удаляются как якобы удалённые файлы. Замена полного индекса не выполняется без успешного обхода всех каталогов; повреждённый MP3 отмечается отдельной ошибкой.
- Удаление источника отменяет его сканирование и исключает запись результатов отменённой задачи; добавление и сброс сериализуются с изменениями источников. Недоступность одной папки не очищает её каталог и не мешает сканировать остальные.
- Одновременно выполняется одно сканирование. Повторный запуск не создаёт конкурирующую задачу. Чтение каталога и воспроизведение остаются доступны во время сканирования.

Ключи генерируются криптографически, хранятся на сервере как хеши, не попадают в URL и логи. Клиенты не имеют административных прав. Проверяются каталог, поиск, обложки, поток и скачивание. Отзыв блокирует новые запросы, включая последующие Range-запросы, и удаляет web-сессии ключа. Уже авторизованный поток может завершиться; клиентская отмена останавливает передачу и закрывает файл. Уже полученные байты и ранее скачанные офлайн-файлы удалить удалённо невозможно.

На телефонах секрет хранится средствами Keychain/Keystore. Для web предпочтительна защищённая HttpOnly cookie-сессия после ввода ключа: браузерный audio element не позволяет произвольно добавлять Authorization headers. Сессия привязана к ключу, отзыв проверяется сервером. Web и API желательно размещать на одном origin. Потребуются ограничение попыток подключения, защита от CSRF и исключение секретов из журналов.

Внешний доступ только по HTTPS. Белый IP не заменяет настройку роутера/Windows Firewall. Подтверждены постоянный белый IP и доступ к настройкам роутера; домена нет. Предлагается бесплатное DNS-имя у DDNS-провайдера и автоматический публично доверенный TLS-сертификат. Конкретный провайдер пока не выбран. Альтернатива — сертификат на IP, если выбранный CA и reverse proxy поддерживают его выпуск и автоматическое обновление. Самоподписанный сертификат не используется как основной способ подключения мобильных клиентов. Развёртывание извне не считается проверенным до проверки из другой сети.

### Flutter

Кандидаты: `just_audio` для воспроизведения, `audio_service` и `audio_session` для фоновой работы и системных команд. Выбор версий и совместимость с автомобильными интерфейсами необходимо проверить прототипом.

Единое состояние очереди обслуживает интерфейс приложения, гарнитуру, экран блокировки и автомобиль. Сохраняются очередь, порядок shuffle, режим повтора и позиция. Обрабатываются аудиофокус, звонки и отключение наушников.

Локальная база хранит плейлисты и метаданные. На телефонах загрузки записываются сначала во временный файл; только завершённый проверенный файл становится доступен офлайн. Нужны возобновление, отмена, удаление и контроль места. Скачанная копия имеет приоритет при воспроизведении. В iOS файлы загрузок не должны включаться в облачный backup. Фоновые загрузки входят в первую версию: на iOS используется background URLSession, на Android — системный механизм фоновой передачи с учётом актуальных ограничений ОС. Flutter-плагин выбирается после проверки обеих реализаций. Очередь задач хранится постоянно; статус восстанавливается после перезапуска. ОС управляет временем выполнения: непрерывное скачивание не гарантируется, а после принудительного завершения приложения пользователем iOS может потребоваться повторный запуск. Проверяются сворачивание, блокировка экрана, потеря сети, перезапуск и отзыв ключа. Секреты задач не попадают в журналы; повторные Range-запросы снова проходят проверку ключа.

Android Auto требует MediaBrowser/MediaSession и дерева каталога; CarPlay — нативной интеграции и соответствующих Apple entitlements. Их доступность и условия подписи нужно проверить до обещания сборки. Тестирование включает симуляторы автомобильных интерфейсов и реальные устройства. Работа обычного Flutter UI и фонового аудио сама по себе их не обеспечивает.

## Этапы и критерии проверки

1. Сервер: сканирование тестовой папки, метаданные/обложки, поиск, Range, ключи и их отзыв, локальная панель, Compose. Проверки доступа, traversal, повреждённых файлов и кириллицы.
2. Сквозной Flutter-прототип: подключение, каталог, воспроизведение, перемотка; ранняя проверка фонового аудио на Android/iOS и возможностей Auto/CarPlay.
3. Очередь, shuffle/repeat, локальные плейлисты, офлайн-загрузки телефонов и восстановление состояния.
4. Завершение Auto/CarPlay, HTTPS-развёртывание на Windows, проверка из внешней сети и инструкции переноса разработки на Mac.

Для тестов используются искусственные или разрешённые небольшие аудиофайлы; личная медиатека в репозиторий не загружается. Сервер собирается и запускается через Docker. iOS собирается в Xcode на Mac.

## Итоги уточнений

- Управление сервером — локальная веб-панель на Windows.
- Белый IP постоянный, доступ к настройкам роутера есть, домена нет.
- Системные фоновые загрузки Android/iOS входят в первую версию.
- При настройке внешнего доступа предстоит выбрать DNS-имя или поддерживаемый вариант TLS на IP. Это не блокирует локальную разработку.
